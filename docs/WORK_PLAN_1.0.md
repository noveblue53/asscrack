**Measurement.** Use one observer’s elapsed-time recording or a common timebase. Note the slower direction of the audio recovery and whether manual action was required. Aim for five seconds on the supported failover topology. Repeat a miss on that topology and investigate it. A persistent miss requires a fix or an explicitly accepted, measured limit in the release notes before shipping. A failed recovery with a viable route, or a need to restart the room, blocks release.

## 1 · Make the room window usable every day

**Outcome.** A user can reclaim space, find actions on the object they concern, and read older chat while new messages or transfers arrive. This milestone stays local to the profile.

**Implement in three reviewable changes.**

1. **Geometry and recovery.** In `index.html` add a visible View button in the room header and focusable separators beside Buddies, the docked map and above Transfers. In `styles.css` keep the existing breakpoints as fresh-profile defaults. Use grid areas and shared size variables for the effective layout. Give Transfers a scrollable body. Let View toggle panels, move Buddies left/right and reset the whole layout. The narrow map remains a dismissible overlay. If width cannot fit a readable chat column plus Buddies, offer Buddies as a drawer. Open one drawer at a time. Reserve room for the composer and Send even when Transfers fills up.
2. **State.** Use one versioned renderer preference in the profile, e.g. `asscrack.layout.v1`. Store preferred buddy width and side, docked-map width, transfer height, and panel visibility. Store CSS pixels, validate finite values/enums on read, recover field-by-field or fall back to defaults. Separate requested sizes from the effective viewport-clamped sizes. A narrow launch must preserve the user's preferred wide layout. Pointer capture, arrows and a reachable reset operate on the same sizing functions. Commit the preference on drag end or keyboard change. Handle cancellation, focus return, stale data and unavailable storage. Defaults must still work with storage disabled.
3. **Commands and reading position.** In `renderer.js` share small action handlers between visible buttons and context menus. Expose a visible row action or keyboard-equivalent menu. Support right-click, Menu key/Shift+F10, arrows, Enter and Escape. Scope the handler to its target. Preserve native editing and selection in inputs, clipboard fields and selected chat text. Use the current state when invoking an action. Close a menu safely if its peer or row disappears. Resolve nested Escape handling so dismissing a menu does not also close the map.

### 1A · Put the conversation and its controls together

Make the room name the main heading with Invite beside it. Put the composer, paperclip, drop target and Send inside the transcript pane. A selected file shows its name and a removable draft before sending. Carry the selected peer ID through the picker, IPC, offer creation and stream authorization. With A sending to B, C must receive no filename, size, hash, descriptor, shelf entry or offer, even when C knows the offer ID. Resolve the recipient at send time. If B has left, show unavailable and preserve the draft. Room-wide sharing requires an explicit room action. Give a received file one inline card with filename, size, sender and the action appropriate to its state. Keep Transfers accessible for concurrent jobs. Expand a group offer by recipient, with independent progress, decline, cancel and failure. An incoming file offers **Show in Explorer** after local verification. For a capable receiver, show **Delivered** only after its size and SHA-256 checks, final save and matching receipt. A session loss, failed transfer or receipt timeout gives **Failed**. For a legacy receiver with no receipt support use **Sent (delivery unconfirmed)** after stream completion. Keep receiver wording and the separate archive label **Saved on this device**. Summarize mixed outcomes per recipient.

Place availability and personal-note editing on the self orb. Keep Join/Mute/Unmute, a secondary Leave voice action, and device settings with the buddy list. Give room history its own room-menu preference and put the clear action with it. Reserve visible status text for changes that matter, such as **Reconnecting…**, or for a local-only send on its message. Put the archive fact **Saved on this device** in message details. A generic checkmark beside each bubble invites a false delivery inference. Make selection, menu access, file outcomes and room recovery understandable with tooltips closed.

**Exit.** At the packaged app’s initial 800 × 600 window and at 1280 × 720, a friend can tell which room is open, attach a file, cancel a draft, send a message, mute without leaving voice, and reveal a completed download. Opening Transfers or inspecting a buddy preserves the current draft and reading position. Confirm a failed or declined transfer identifies the affected person. Check new message arrivals, and retain milestone 1’s keyboard, splitter and narrow-window tests.

**Receiver retry.** Disconnect one recipient mid-download and verify they can retry from their existing card or Transfers row when the original source returns. Retry starts a new attempt at byte zero and reports success after final size and SHA-256 verification. Check source availability, repeated clicks, partial-file cleanup and another recipient’s independent transfer on direct and relayed paths.

## 3 · Put manual availability on the buddy list

**Outcome and scope.** From the self orb or its visible menu choose Available, Away or Do Not Disturb and a note of up to 80 Unicode code points. Display a small, text-labelled badge alongside the existing voice and host indicators. DND suppresses optional local attention sounds and popups as those features ship. It leaves chat delivery and voice controls working. Keep status local to the current login initially. Restore it on transport reconnect within the running app. On a fresh interactive launch start Available. A launch directly into Idle Peer follows 5F and advertises the computer’s idle role.

**Entry and prerequisites.** In `node.mjs` add one optional typed presence control to the open chat session. Before choosing the wire encoding, pin the source revision used for the 0.6.0 release, inspect its receive path and send a harmless unknown typed control between ordinary chat messages in a mixed-version session. Check that chat continues and the control produces no visible message or history entry. Record the revision and result. If it fails, negotiate support through a path the old client already tolerates before sending presence. Send the current snapshot when a session opens and on change. Use the authenticated open session in keyed rooms and the established peer session on LAN. Match updates to the current session before updating the peer-ID map. Discard remote state on leave and ignore delayed close events for a replaced session. Carry the event through `main.js`, `preload.cjs` and `renderer.js`. Include a current-state read after renderer subscription/login so an early event cannot strand the UI. Presence is ephemeral and requires no history record or persistent person ID.

**Exit.** A changes to Away with a note, B sees it, C joins later and immediately sees the same state. Drop/reopen the A–B session, then restart A with the same display name and a new peer ID. Verify the stale row disappears, the restored or fresh state matches the rules, and DND never changes the mic mute/speaking mark. Pair new and pinned older clients both ways. The new client shows status unknown for the old buddy and the older client continues normal chat. Exercise two identical display names.

### 3A · Give the room a one-line topic

Show one editable line above the transcript, for example “iRacing at 8 · one seat open.” A visible **Edit topic** action and `/topic <text>` invoke the same handler. `/away [note]` uses milestone 3’s existing availability setter and 80-code-point note limit. Provide a discoverable return to Available. A topic is shared room state. A person’s away note belongs to that login. The optional conversation tabs in milestone 7 address simultaneous discussions.

For the first slice, any current member can propose a topic. Let the elected host order accepted edits and distribute the current value to late joiners. Carry the last accepted topic through host failover while a capable member retaining it is present. Define how a stale snapshot is rejected. If the current host lacks support, show the feature as unavailable. Support clearing the topic. Scope retention to the live room for this slice.

**Exit.** A sets the topic and B goes Away. C joins late and sees both. A disconnects and the surviving members retain the agreed topic. B disconnects and B’s availability disappears. Have two users edit nearly simultaneously, then verify agreement after failover. Clear the topic and have C reconnect. Check that an older client can still chat.

## 4 · Send a screenshot directly in chat

**Outcome.** Paste a Windows screenshot, add a caption, preview it on a second client and optionally save the byte-identical offered PNG. Keep a text card meaningful for peers who missed the transfer or use an older version.

Provide Cancel before sending. For path-backed files reuse the existing file path workflow. Hash the original once before offering and show Preparing for a large file. Treat the staged PNG as the original for clipboard comparisons.

In `node.mjs` keep the ordinary untyped chat record with meaningful fallback text (filename, size and caption). Add optional validated attachment metadata with a unique descriptor ID, content hash, original size, media kind and display name. Keep binary data and filesystem paths out of history. Use the same validation and projection in live parse, buffer insertion, host merge, history event and renderer. Return the canonical message ID/time to the local UI alongside the send count via a compatible app-level path. Reuse the canonical message ID and time already returned by the 0.7.0 send path. Deduplicate by message ID. Correlate offer and card by descriptor/offer identity regardless of arrival order. Keep authorization tied to the peer and offer. Two equal files in separate posts are still two posts.

**Availability.** The original offer currently targets peers connected at posting. A new client receiving only history can show “Original unavailable” unless it already has a verified local copy or a source confirms a fresh eligible offer. When the sender remains online, support an explicit request followed by a fresh offer to that requester for the same content. On sender departure update the action, keep the caption and any cached preview. A surviving receiver's saved copy remains accessible locally. Define expiry for the sender's staged file and surface expiry before showing Download. On an old host, history strips optional fields. The readable fallback survives, and a client must accept that rich cards may degrade to text on replay. Keep the ordinary transfer offer usable by older receivers. Give a targeted buddy send a private offer only, never a room-wide descriptor.

**4B · Actual inline preview.** Start with static PNG thumbnails. A capable receiver can request a separate bounded derivative from a capable sender after it gets the card. Negotiate preview support with an optional typed control after session open. A peer that never advertises it receives the readable chat line and ordinary file offer only. Use a dedicated, limited data stream or transfer path with a preview role, separate from the original-download action. Render only a verified local derivative. A recommended initial trial budget is 512 KiB encoded, 1024 px longest edge, 1 megapixel decoded, two concurrent previews and 32 MiB of disposable local preview cache. Bound input decoding and total work as well. Use a narrowly scoped local media URL and adjust the existing self-only CSP only as needed. Provide automatic thumbnails off / on, and always allow manual original retrieval subject to receiver preference, disk availability and filesystem constraints. Enforce space/write errors during transfer. Keep originals streamed, with no fixed application-wide size cap. Archives and unknown files stay download-only.

**Prerequisite and exit.** Prove card survival across current-client live, history and host-election paths before shipping previews. Extend `test/history.test.mjs` and `test/file-transfer.test.mjs`; keep the existing interruption cleanup behavior. Two profiles: paste a real screenshot, send it with a caption, verify inline pixels without saving the original, then save and compare SHA-256 to the staged PNG. Exercise disabled previews, oversize or malformed thumbnails, receiver cancel, insufficient disk, old host replay, late join with sender present and absent, and the one-copy UI when offer and card arrive in either order. Compare the final size/hash, try corrupted partials, a changed source and an older recipient, and confirm expiry releases disk. Record direct/relay, OS, RAM high-water mark, file size and actual bytes retransmitted. Consider optional peer-held copies only if original-source absence proves to be a separate frequent problem. Require explicit sharing consent, expiry, source eligibility and a verified hash before advertising another peer as a source.

## 9 · Run a one-command ready check when the group wants it

Make `/ready Race in five?` and a visible **Ready check** action open one live prompt with **Ready** and **Give me a minute**. Show names, responses and who has yet to answer. Identify voters by the current peer session. A changed vote replaces the previous one. Keep responses session-only and respect DND. Let the initiator close the check and expire it if the initiator leaves. An older client can keep chatting.

**Exit.** Three friends respond, one changes their vote and two share a display name. Each person counts once. Reconnecting or replaying history cannot resurrect a closed check. Build this when the group actually wants it. Keep threads and reactions on the later-ideas list.

## 1.0 · Three game nights and the ship decision

Run three ordinary game nights with at least three friends across at least two networks. A night can cover several field checks. Use the early result to guide work and the final night to verify the distribution candidate. Record rescues, restarts, fallbacks, audio gaps and the exact build. If a support issue derails a night, keep the observation, repair the fault, and repeat the affected scenario until there are three qualifying nights.

| Night | Put the app in someone else’s hands | Required observation |
| --- | --- | --- |
| 1 · Join and keep talking | Give a friend the identified pilot executable and an invite. Use the room normally. At a convenient point, remove the active host with a viable alternate. | A friend reaches voice without a walkthrough. The group finishes the session, with measured voice and chat continuity or recovery. Fix a failed route before further feature expansion. |
| 2 · Return tomorrow | Close all processes between nights. Someone other than the original host opens the saved room first. Verify their opted-in history offline, then reconnect from another network under the documented reachability conditions. | The same credential opens the same room. Locally saved lines appear once. A peer using a valid reachable invite can rejoin. Across nights 2 and 3, also show that a late friend can collect a shelf file while its publisher remains online. |
| 3 · Use the final candidate | Have friends use the identified 1.0 executable for the whole session. Exercise mute, catch-up, status, topic, shelf and an actual host loss. Use the normal UI and distribution file. | People correctly identify mute and connection state, get the intended file and keep talking through the supported failover. Nobody needs the developer to repair the room or move the group to another app. |

**Go/no-go rule.** Ship when all required release-order exits, packaged storage and upgrade checks, Phase 8 field cases, and three qualifying nights have recorded passes or the specifically accepted timing limit. Earlier results count while the relevant code, storage format, dependencies and routes still match. If the candidate changes, issue a new hash, repeat the affected checks and confirm normal join, chat and voice on the actual final binary. Changes to networking, audio, archive handling or packaging after the final night require another candidate session covering the changed behavior. Missing field access means “awaiting field verification.”

Block publication for a reproducible failure of supported join or failover, archive loss or plaintext exposure contrary to the storage promise, wrong-room history, silently lost or duplicated accepted messages, a corrupt or wrongly shared file, or an unusable upgrade. For a nonblocking cosmetic issue, record its effect and a follow-up. Keep optional enhancements out of the ship decision.
