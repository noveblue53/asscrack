In `node.mjs` keep the ordinary untyped chat record with meaningful fallback text (filename, size and caption). - In Electron’s main process, put the saved-room catalogue and messages under the active profile’s `userData`. Use a full-width, versioned room fingerprint derived from the decoded room key and exact room-name bytes, with unambiguous encoding. The display name, mutable invite text, peer ID, and existing eight-hex-digit discovery tag are unsuitable archive identifiers. Existing caches are hints. Older installations can import a v1 invite to recover the credential those caches lack.
- Prove a maintained SQLCipher binding in the repository’s actual portable build before depending on it throughout the app. Generate a random profile database key, wrap it using Electron’s Windows `safeStorage`, and put the room credential inside protected storage. Keep key handling in the main process and expose narrow room operations over preload IPC. Recover safely from interrupted initialization. If a key is missing or cannot be unwrapped, preserve the archive, report it as locked and allow retry. Plaintext fallback or silent replacement would lose the promised protection or the data. If packaging the binding fails, try a supported build or binding on the pinned Electron runtime. Continue independent work while Windows verification is pending.
- Build the smallest usable slice first. Save a room and one real chat line through the normal UI, close every process, disconnect the network, restart the packaged executable under the same Windows account and read the line. Open a second room with the same display name and a different key. Each room must show only its own chat. Verify moving or replacing the executable under the same account still finds the profile.

### 2. Make live chat and the archive agree

- Have the node assign one canonical message ID and timestamp per outgoing send. Return that record through IPC so the renderer and archive use the same identity. The baseline renderer creates its own timestamp before the node returns. Preserve the existing wire format and legacy-ID normalization. When zero sessions accept a send, show that status explicitly. Keep that entry local and exclude it from future host replay.
- Persist accepted outgoing and incoming live records once per `(room ID, message ID)`. Keep their source distinct from host replay and archive reads. A live record that was already displayed through replay must still be eligible for saving once. Use the database uniqueness constraint for durable deduplication. The current 200-entry buffer forgets evicted IDs. Page older rows into the UI and preserve reading position while live traffic arrives.
- Serialize save-toggle, clear, forget and queued writes for a room. A queued write accepted before Clear must never restore a deleted row. Handle a full disk or failed write without claiming the message was saved. Choose and document concrete per-room retention and byte limits. Pruning must preserve the newest eligible rows, with enough room for the 250-message acceptance case.

### 3. Restore peer connections and recent history

- Load the saved credential through the existing keyed login path. Only **Create room** generates a new room key. Merge validated cached endpoints with invite endpoints so an old invite cannot overwrite a newer working address. Retain the existing retry at a bare endpoint when a peer ID changes. Treat manual addresses, UPnP mappings and cached addresses as candidates until a peer actually connects.
- Prepare the host’s bounded replay window before any new session or host-election event can publish it. Seed it with up to 200 recent shareable records retained by that device, then incorporate eligible live traffic. Apply the existing host-authority rule on incoming replay. Keep ordinary replay available in memory when local saving is off. Clear and Forget must also invalidate pending archive reads and any replay window seeded from deleted rows, so the device cannot republish them from a stale snapshot.
- Preserve the keyed room proof before releasing history. Bound incoming frames by encoded bytes before buffering them in full. Bound history batches by count and bytes, validate records, and ensure the sender emits batches the receiver can accept. Review the chat, file, voice and relay entry points for their actual admission checks and resource limits. Fix issues introduced or exposed by durable chat. Record unrelated findings separately.
- Update the user-facing explanation of encryption. Noise protects peer connections. A circuit relay can see connection metadata, and an application host that forwards voice can access the audio. Windows account protection covers the local archive and saved invite. Software running as the signed-in Windows user is outside this protection. A recipient can keep a copy, and files explicitly saved to Downloads follow normal file behavior. Existing diagnostic logs and route caches may expose connection metadata. Keep message bodies, complete invites and secrets out of them.

### 4. Run the release checks

Use two Windows PCs on different networks for the internet cases. A fresh profile on one PC can act as a newcomer. Keep a separate copy of the byte-for-byte original invite. Reset fixtures between scenarios. Use numbered messages and record expected IDs and counts so cached routes, peer replay or duplicate UI rows cannot accidentally produce a pass.

| Check | Pass condition |
| --- | --- |
| Full shutdown and offline reopen | A and B exchange 250 short numbered messages, including sends from both PCs. Close both. B, the original joiner, reopens first with networking disconnected. Its 250 messages appear exactly once. A second same-name room contains none of them. |
| Original and refreshed invites | Restart the reachable peer at its original endpoint and record its changed peer ID. A clean remote profile uses the original invite and exchanges a new message. Then retire the only old endpoint. A fresh profile using the old code waits. A refreshed invite sent out of band reaches the new endpoint. An existing member using it sees the same saved transcript. |
| Host order and late join | With a host that retained all 250, a newcomer receives IDs 51–250. Repeat with a host that retained only a known smaller set and a second member with all 250. The newcomer gets the host’s eligible set. The richer archive survives locally. Host change and repeated replay produce no duplicate visible or saved IDs. Include a baseline v1 peer in a join/chat/replay check. |
| Clear, saving off and simultaneous writes | B clears its saved 1–250. A replays 51–250 and sends live 251. Offline reopen on B shows only 251. Turn saving off, restart with it off, receive 252, then turn it on for 253. B’s archive contains 251 and 253. Repeat Clear with a pending write. Forget B’s room and verify A can still reopen its own copy. |
| Packaged storage and recovery | Read a test record with the correct key. Verify ordinary SQLite and a wrong key cannot read it. Confirm the packaged binding reports a SQLCipher version. On disposable copies, interrupt a write and reopen to the last committed state. A missing wrapper or a different Windows account must leave existing data recoverable by the original account with its wrapper. Exercise the actual journal/WAL mode, require memory-backed SQL temporary storage, and check app-written files and logs for a distinctive test message and invite. |
| Bounds and regressions | Exercise the documented message, batch and retention boundaries and a controlled storage-write failure. Check the saved/unsaved status, existing LAN chat, file transfer, voice and room-window behavior. Run the full suite and start the final portable build. |

## 7 · Decide whether text topics earn their tabs

**Gate.** After the quote trial, proceed if the same group wants two recurring streams on both evenings and can name what belongs in each. Otherwise keep one conversation and revisit when a group regularly holds simultaneous discussions.

**First trial.** General plus public text topics, one roster, invite and voice session. A compact prototype can use the ordinary message text as the durable carrier. Reserve a visible prefix such as `[#builds] ` for topic posts. Use immutable room-local lower-case slugs (1–24 ASCII letters, digits or hyphens, reserving general) as IDs. Same slug converges across creators. Render the prefix as a tab label on new clients, and show it as readable text on old ones. Define the convention openly: a manually typed exact valid prefix opts into that topic. Leave other text in General. To guarantee historical untagged content remains in General, check old fixtures, document the prefix collision case, and provide a literal-prefix escape for new posts. If the group requires perfect classification of pre-feature text, use validated versioned metadata and accept General fallback after an old host replay instead.

**Scope and entry.** `renderer.js`, markup and styles handle tabs, selected view, per-topic counts and draft preservation. Discover tabs from retained posts. A new empty tab is local until first posted, and a tab with no remaining history may disappear for late joiners. Keep the existing room-wide 200-message window. This prototype requires no host-owned topic catalog, ACL, permanent history or schema migration. Explain to users that every room member receives every topic.

**Exit.** Two new peers post to General and two topics. An older peer sees readable posts in its flat stream. Late join, change hosts (include an old host), and reopen a compatible client. Retained tagged posts must reconstruct in the same topic without duplicates. Exercise same-slug creation, unread during replay, ordinary legacy text, literal prefix, and eviction of the last message in a topic. If people want permanent empty topics, renames, or independent retention, design a replicated catalog and mixed-version migration as a separate decision.

## 8 · Resume large transfers only when real transfers justify it

**Gate.** Measure a representative original over a direct route and a relayed route; start with 1 GiB if disk and time allow. Record bytes, topology, elapsed time, interruption point and cost to restart. A same-PC rate cannot predict a friend's upstream. Proceed when real interruptions or restart times are a recurring burden.

**Slice.** Add an opt-in retained partial, keyed by verified content hash and size, with a retention budget, visible expiry and discard. Version the file transfer protocol for offset negotiation, validate the partial and source, seek both ends, and verify SHA-256 across the complete output before finalizing. Treat cancellation as discard unless the user explicitly selects Pause. The current one-shot sender and eager partial cleanup require deliberate changes in `file-transfer.mjs`. A peer with only v1 gets a fresh full transfer and an explicit restart indication.

**Exit.** Interrupt the representative transfer near 40%, reopen over a different available route and confirm from byte counters that the uploader sends the remainder plus protocol overhead. Compare the final size/hash, try corrupted partials, a changed source and an older recipient, and confirm expiry releases disk. Record direct/relay, OS, RAM high-water mark, file size and actual bytes retransmitted. Consider optional peer-held copies only if original-source absence proves to be a separate frequent problem. Require explicit sharing consent, expiry, source eligibility and a verified hash before advertising another peer as a source.

## 9 · Run a one-command ready check when the group wants it

Make `/ready Race in five?` and a visible **Ready check** action open one live prompt with **Ready** and **Give me a minute**. Show names, responses and who has yet to answer. Identify voters by the current peer session. A changed vote replaces the previous one. Keep responses session-only and respect DND. Let the initiator close the check and expire it if the initiator leaves. An older client can keep chatting.

**Exit.** Three friends respond, one changes their vote and two share a display name. Each person counts once. Reconnecting or replaying history cannot resurrect a closed check. Build this when the group actually wants it. Keep threads and reactions on the later-ideas list.

## Build and upgrade the 1.0 candidate

1. Prepare the release commit on main with package and lockfile version `1.0.0` and the README/changelog for the actual feature set. On Windows, check out that exact commit in a clean worktree and record its SHA. Use the project’s supported Node version and lockfile. Run `npm ci`, `npm test`, `npm start` and `npm run dist`. Save the resulting `dist/ASSCRACK-1.0.0-portable.exe`. Record size, SHA-256 (PowerShell `Get-FileHash -Algorithm SHA256`), source SHA, architecture, Windows, Node and Electron versions. Keep the build that produced the field evidence.
2. On a fresh Windows profile, launch the packaged file from the normal desktop workflow. Test first and second launch, microphone access, join, mute, chat, transfer, quit and reopen. Confirm a second launch focuses the existing window and a clean quit permits replacement. Exercise the native encrypted database by saving a room and reading a saved line after an offline restart.
3. On a disposable copy of a real 0.6.0 profile, record the existing name, settings, known endpoints and original invite. Close all instances, replace the executable and launch under the same Windows account. Reuse the invite to join, opt in to local history, exchange a known line, close, move the executable and reopen offline. Check the room and line are recovered exactly once. A legacy cache that lacks a room credential should offer invite entry. Old in-memory history can only be recovered if a reachable peer still holds eligible lines.
4. Pair the candidate with the actual 0.6.0 binary. Swap who hosts. Check baseline join, chat, readable quotes, ordinary file offers and voice where the tested versions support it. Verify optional presence/topic/shelf controls degrade as specified and never enter chat history as garbage. Verify that the candidate labels a send made alone as local-only and excludes it from later host replay. Record exact versions and any user-visible limitations in release notes.
5. Retain a pre-upgrade disposable profile copy and the prior executable for a recovery rehearsal. If a migration, archive key or disk operation fails, preserve the user’s original data and give a recoverable error. Use a copied profile for downgrade investigation. Document what an older executable can actually reopen before suggesting a rollback.

## 1.0 · Three game nights and the ship decision

Run three ordinary game nights with at least three friends across at least two networks. A night can cover several field checks. Use the early result to guide work and the final night to verify the distribution candidate. Record rescues, restarts, fallbacks, audio gaps and the exact build. If a support issue derails a night, keep the observation, repair the fault, and repeat the affected scenario until there are three qualifying nights.

| Night | Put the app in someone else’s hands | Required observation |
| --- | --- | --- |
| 1 · Join and keep talking | Before the shelf is built, give a friend the portable executable and an invite. Use the room normally. At a convenient point, remove the active host with a viable alternate. | A friend reaches voice without a walkthrough. The group finishes the session, with measured voice and chat continuity or recovery. Fix a failed route before further feature expansion. |
| 2 · Return tomorrow | Close all processes between nights. Someone other than the original host opens the saved room first. Verify their opted-in history offline, then reconnect from another network under the documented reachability conditions. | The same credential opens the same room. Locally saved lines appear once. A peer using a valid reachable invite can rejoin. Across nights 2 and 3, also show that a late friend can collect a shelf file while its publisher remains online. |
| 3 · Use the final candidate | Have friends use the identified 1.0 executable for the whole session. Exercise mute, catch-up, status, topic, shelf and an actual host loss. Use the normal UI and distribution file. | People correctly identify mute and connection state, get the intended file and keep talking through the supported failover. Nobody needs the developer to repair the room or move the group to another app. |

**Go/no-go rule.** Ship when all required release-order exits, packaged storage and upgrade checks, Phase 8 field cases, and three qualifying nights have recorded passes or the specifically accepted timing limit. Earlier results count while the relevant code, storage format, dependencies and routes still match. If the candidate changes, issue a new hash, repeat the affected checks and confirm normal join, chat and voice on the actual final binary. Changes to networking, audio, archive handling or packaging after the final night require another candidate session covering the changed behavior. Missing field access means “awaiting field verification.”

Block publication for a reproducible failure of supported join or failover, archive loss or plaintext exposure contrary to the storage promise, wrong-room history, silently lost or duplicated accepted messages, a corrupt or wrongly shared file, or an unusable upgrade. For a nonblocking cosmetic issue, record its effect and a follow-up. Keep optional enhancements out of the ship decision.

## Publish and verify the release

1. On the tested source, finalize the release notes with the network conditions, measured recovery, privacy boundaries, mixed-version behavior, archive retention, supported Windows environment and known limitations.
